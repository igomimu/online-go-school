# Lessons — online-go-school

## 2026-09-01: 生徒リストのアイコンは講師から見た入出力で表す
- **訂正**: 内部名の M/S をそのままアイコンへ対応させると、講師の操作感と逆になる。三村さんの本格使用初回で判明した。
- **決まり**: マイクは「講師の声をその生徒へ届ける」、スピーカーは「その生徒の声を講師が聞く」。内部の `canHear` / `micAllowed` や旧M/S呼称ではなく、講師が何を送る・聞くかでラベルとアイコンを決める。

## 2026-08-30: 旧画面の M/S/共有を一般的な音声ボタンとして読み替えない
- **事象**: 講師画面の「Sをクリア」「Mをクリア」「共有を全員に」を、講師自身の音声操作や曖昧な復旧ボタンとして説明してしまった。
- **教訓**: この3操作の対象は参加中の生徒全員。Mは生徒マイク、Sは生徒が講師の声を受信する状態、共有は生徒へ検討を見せる対象を表す。旧Windows版由来の短いラベルは、列・対象者・一括操作の関係をコードと運用の両方で確認してから意味を説明・実装する。

## 2026-08-23: 意図的な全件DELETEにもWHEREを明示する
- **事象**: 生徒区分マスターをトランザクション内で全件入れ替える関数に `DELETE FROM table;` を使い、Supabaseの「DELETE requires a WHERE clause」安全検査に止められた。
- **教訓**: 全件入れ替えが意図どおりでも、Supabaseへ載せるSQLのDELETEには必ず述語を明示する。全件対象なら `WHERE true` とし、マイグレーションの文字列検査だけでなく、本番と同じ経路でRPCを実行して完了まで確認する。

## 2026-08-23: マスター項目の削除は参照中データの移行までを一操作にする
- **事象**: 使用中の生徒区分を削除すると、DB側の保護処理が保存全体をエラーにした。画面側の事前判定だけでは、キャッシュや取得範囲の差で防ぎ切れない。
- **教訓**: 選択肢マスターを削除可能にするなら、参照中データをどうするかをDBトランザクションに含める。今回は削除対象の生徒を「未設定」へ移してからマスターを削除し、画面では影響人数を確認してから実行する。

## 2026-08-15: 同じ時計で音声と文字の時間方向を揃える
- **事象**: 秒読み音声は「10秒、20秒…」と経過秒を読む仕様なのに、画面は内部の残り秒をそのまま表示してカウントダウンしていた。
- **教訓**: 時計の内部値（時間切れ判定用の残り時間）と利用者向け表示は分ける。音声と文字が同じ概念を示す画面では、増減方向・丸め・回の切替まで同じ仕様としてテストする。

## 2026-08-02: 授業配信の生徒画面は講師操作に従う閲覧専用
- **事象**: AI結果を生徒へ同期した際、生徒自身も候補手をホバーしてPVを切り替えられる設計にしていたが、授業では講師が示す手順を全員が同時に見ながら説明を受けるのが目的だった。
- **教訓**: 講師主導の授業画面では、データの同期だけでなく操作権限も同期設計に含める。生徒側の同種操作を無効にし、講師の選択・開始・終了を単一の表示権威にする。

## 2026-08-02: 操作感だけでなくAI探索条件も参照元と揃える
- **事象**: Pocket KataGo型の表示・二段階解析を移植したが、深い解析の標準値はPocket KataGoの3000 visitsに対しオンライン側が1000 visitsのままだった。
- **教訓**: 参照アプリと同じAI体験を再現する時は、UI・操作・API接続だけでなく、探索数、モデル、コミ、候補数、PV長など推論条件も比較表で確認する。既存localStorageが旧探索数（100〜1000等）を保持する場合は、既定値変更だけで完了とせずバージョン付き移行を用意する。

## 2026-08-01: API疎通だけでAI画面の修正完了と判断しない
- **事象**: KataGo APIがHTTP 200を返し、重複リクエストも止まったことを確認したが、実際の先生画面ではAI表示が使える状態にならず、生徒側にはAI結果自体が配信されていなかった。
- **追加原因**: 生徒が `REVIEW_START` を受けて検討モードへ入っても、直後の `BOARD_UPDATE` で `syncedNode` が作られると、自動ビュー判定が検討モードを授業モードで上書きしていた。データ受信だけでなく「最終的にどの画面が描画されるか」まで追う必要がある。
- **教訓**: AI機能は「API成功」「先生UIのON/OFF・候補表示」「先生から生徒への結果同期」「OFF時の中断」を別々に検証する。特に配信授業では先生側だけのローカルstateを完成扱いにせず、実際の先生・生徒画面を同時に開いて表示を確認する。

## 2026-08-01: 調査前にリモート最新版を確認する
- **事象**: 入室画面の表示崩れ調査で、最初に手元の古い作業ツリーを前提に確認を始めてしまい、三村さんから「プルして確認して」と訂正を受けた。
- **教訓**: 継続開発中のプロジェクトは、調査開始時に必ず `git fetch` とローカル/`origin/main` の差分を確認する。既存作業ツリーが汚れていてpullできない場合は、変更を退避・破棄せず、取得済みの `origin/main` から隔離worktreeを作って最新版を検証する。

## 2026-07-18: 生徒照合で名前をキーにしない
- **事象**: 1002と1003のように別IDだが同じ名前の生徒で、棋譜履歴や対局中表示が同じ生徒として扱われる危険があった。
- **根因**: `sid:<id>` / bare ID の揺れを吸収する過程で、生徒名も照合候補に混ぜていた。名前は表示名であり一意キーではない。
- **教訓**: 棋譜保存、履歴検索、対局中判定、接続中判定では、ID・ログインコード・`sid:`付きIDだけをキーにする。名前は表示専用。旧データ救済で名前を使う場合も、IDが無いときだけに限定する。

## 2026-06-13: E2E緑でも実ユーザーで死ぬ「状態乖離」パターン
**事象**: 先生PWサーバー再設定後、三村さんが正しい新PWでログイン不能。E2Eは13/13緑だった。

**根因**: ローカル localStorage のPW照合がサーバー認証より先に走るゲートが残っていた。
E2Eヘルパーは毎回 `setupTeacherPassword(TEST_TEACHER_PASSWORD)` でローカルとサーバーを
**同じ値に揃えて**いたため、「ローカル≠サーバー」という実ユーザーの状態を一度も踏まなかった。

**教訓**:
1. **二重に保存された真実（ローカルキャッシュ vs サーバー）があるなら、E2Eに必ず「乖離ケース」を入れる**。
   揃った状態だけのテストは、揃っていることのテストにしかならない。
2. サーバー側の認証情報を変更したら、「既存ブラウザ状態（古いキャッシュ）からの初回ログイン」を必ず実機 or E2Eで踏む。
3. 認可の権威を移行するときは、旧権威のコード（照合・リセットUI）を**残さず撤去**する。
   並存させると「どちらかが通れば入れる/どちらかが落ちれば弾く」の混在で必ず事故る。
   → 対応済み: `e2e/teacher-auth.spec.ts` に乖離ケース2本を常設（commit 481b962）。

## 2026-06-30: 競合分析でブランド資産を機能比較に矮小化しない
**事象**: online-go-school の市場比較で、横浜囲碁サロン・ダイヤモンド囲碁サロン・洪道場の強みを「商品設計」「講師陣」「本格派」程度に薄くまとめてしまった。

**根因**: 競合の選ばれる理由を、機能・価格・提供形態に寄せすぎた。実際には、横浜囲碁サロンは囲碁YouTubeでの成功と発信者への信頼、ダイヤモンド囲碁サロンは都心一等地の高級サロンと女性アマチュアインストラクターの魅力、洪道場は日本最強棋士を何名も排出した実績ブランドが中核。

**教訓**:
1. 教室・サロン・教育サービスの競合分析では、機能表の前に「なぜその人・場が選ばれているか」を書く。
2. ブランド、人物像、場所の空気、実績、継続接触は、価格や機能と同等以上の購買理由として扱う。
3. 三村側の比較では、システム利便性だけでなく、三村九段の人柄・教室の継続感・保護者の安心感を必ず評価軸に入れる。

## 2026-07-08 「スクショで確認済み」と言いながら画像を見ていなかった
- **事実**: PWAボタンの本番検証でinnerText検出とconsoleログだけを見て「両画面で確認済み」と報告。実際は①先生の実動線（ログイン直後の教室管理画面）にボタンが存在しない②下部バーが#rootのpadding分（64px）ビューポート外に見切れ、の2点を見逃した。三村さんの実機指摘で発覚。

## 2026-07-09 「手番でない側でも石を置ける」が何度も直らなかった
- **事実**: 対局で手番側だけが着手できる仕様が繰り返し直らなかった。真因は、先生が対局のプレイヤー（黒/白）を兼ねると `isTeacher` フラグが手番チェックを全て素通りさせ、かつ `effectivePlayer` が先生自身の色で着手していたこと（黒手番でも白石が置ける）。サーバー(submit_move)は step3 で手番を検証し409で拒否していたが、クライアントが楽観的更新+LiveKit配信を先に走らせるため、相手の盤面に石が残って食い違い、「置けてしまう」ように見えていた。
- **教訓**:
  1. 「バリデーションが効かない」系は、まず権威(サーバー)が本当に通しているのか確認する。ここではサーバーは正しく拒否していた＝真の症状は「楽観的更新/ブロードキャストのロールバック漏れによる盤面desync」。「サーバーが検証していない」と決めつけない。
  2. ロールのバイパス（isTeacher で全チェック免除）と、色の導出ロジック（effectivePlayer=myColor）が別々にあると、両者の組み合わせで抜け穴ができる。権限フラグを「全部免除」に使わず、条件を分ける（isProxyTeacher = isTeacher && !isParticipant）。
  3. 手番系は「打とうとしている色 === その局面の手番の色」という単一の不変条件をコードで明示すると、ロールに依存せず封じられる。

## 2026-07-10: mainの巻き戻しを「事故」と決めつけて復元した誤判断
- 別AIのcommitがmainから強制的に消えていたのを「force push事故」と推定し、cherry-pickで復元してしまった。実際は三村さんが指示した意図的なrevert（別AIがネット囲碁学園=igocampusの問題を三村囲碁オンラインと錯覚して実装したため）。
- **2026-07-11: 状態変数 (State) のセッター消し忘れと自動切替競合バグ**
  - **事象**: `activeGameSource` を削除した際に、`setActiveGameSource` の呼び出し箇所が残っていたため、実行時に生徒側画面がクラッシュし、E2Eテストがタイムアウトした。また、手動で「手番ではない盤」に切り替えた際、自動遷移 useEffect が即座に手番の盤へ引き戻してしまい、E2Eテストが落ちた。
  - **教訓**:
    1. 状態変数を削除した際は、対になるセッター関数の消し忘れがないか徹底的に grep で確認する。コンパイルが成功しても実行時エラーで画面クラッシュの原因となる。
    2. 自動切替 useEffect が手動アクションと競合する場合、対局状態ハッシュ（手番と手数）を監視し、「対局自体に進行があった時のみ自動遷移を判定する」設計にすることで、手動選択による切り替えを阻害せず競合を回避できる。

## 2026-07-14: git add -A で意図的な未追跡ファイルを誤コミット
- **事故**: `git add -A src e2e ...` が、意図的にgit管理外としていた検証道具（e2e/proof-*.spec.ts）を拾い、publicリポジトリにpushした。秘密情報は無かったが運用違反。
- **ルール**: commit前に `git status -s` の `??`（untracked）を必ず確認し、追跡対象は**ファイル名を明示して add** する。ディレクトリ単位の `git add -A <dir>` は untracked を巻き込む前提で使う。意図的な未追跡ファイルは発見した時点で .gitignore に載せる（今回 proof-*.spec.ts を追加済み）。

## 2026-08-04: 型チェックが空振りしていた（`npx tsc --noEmit` は1ファイルも見ていない）
- **事故**: 「tsc 通過」と何度も報告しながら push した結果、YOGAPro から「型エラーでビルドできない、本番は1コミット前のまま」と指摘された。
- **原因**: このリポジトリの `tsconfig.json` は `{"files": [], "references": [...]}` の参照専用。`npx tsc --noEmit` はこの構成では**何も検査しない**。実際のビルドは `tsc -b`。
- **ルール**: 型の確認は必ず `npm run build`（`tsc -b && vite build`）で行う。`npx tsc --noEmit` を「型チェック済み」の根拠にしない。
- 併せて: 型述語（`value is T`）が絞り込むのは**渡した変数**であって式ではない。`isTheme(value ?? null)` と書いても `value` は絞られない。`??` は呼び出しの外で済ませる。

## 2026-08-04: コントラスト監査が文字しか測っておらず、入力欄の枠を見逃した
- **事故**: 「主要8画面のコントラスト指摘 112件→0件」と報告した後、三村さんから「文字入力欄が見えない」。測ると入力欄の枠と面の差はライト1.45:1・ダーク1.25:1で、UI部品の輪郭に要る3:1を大きく下回っていた。全画面の入力欄18箇所が同じ状態だった。
- **原因**: 自作の監査が**文字色と背景色の比だけ**を測っていた。枠線・境界といった非テキストの輪郭を対象にしていなかった。
- **ルール**: コントラストを検査するときは文字（4.5:1）と**UI部品の輪郭（3:1）**を別に測る。「0件」と言う前に、その検査が何を見ていないかを明示する。
- 併せて: 飾りの罫線と入力欄の枠に同じトークンを使わない（`--color-line` と `--color-field-line` を分けた）。

## 2026-08-04: デプロイ確認のポーリングで Vercel のセキュリティチャレンジを踏んだ

## 2026-08-04: 本番から外した「強制終了」が本番でこそ必要だった
- **事故**: 7/22 に「テスト時しか使わない」として対局の強制終了ボタンを `import.meta.env.DEV` 限定にした。8/4 に三村さんから「設定間違いで対局を開始した場合に講師が中断するには？」と聞かれ、**本番に手立てが無い**ことが判明した。

## 2026-08-04: E2Eの残骸が別のテストを壊す
- **事象**: `simul-game` が単体でも落ちるようになった。原因は8/1の `byoyomi-voice` が残した status=playing の対局6件。テスト生徒に進行中の対局があると、新しく作った対局が講師の一覧に現れない。
- **原因**: 各 spec は `finally` で teardown するが、実行を強制終了すると走らない。
- **対策**: seed のたびにテスト生徒（1010/1011）の進行中対局を消すようにした（`clearStaleTestGames`）。前の実行がどう終わっていても揃った状態から始まる。
- **教訓**: 後片付けを finally に置くだけでは足りない。**始めるときに掃除する**方が強い。

## 2026-08-05: StrictMode の二重実行で、開いた別ウィンドウを自分で閉じていた
- **事象**: 検討を別ウィンドウ（`window.open` + createPortal）に出したところ、E2E が掴んだウィンドウは中身が空で `closed=true` だった。ウィンドウは2つ生まれていた。
- **原因**: 開発時の StrictMode は effect を「実行→後片付け→もう一度実行」と2回走らせる。後片付けで即座に `win.close()` していたため、1回目のウィンドウが閉じられ、2回目で別のウィンドウが開き直されていた。最初のウィンドウを掴んでいた側（E2E・呼び出し元）は抜け殻を見ることになる。
- **対策**: 閉じるのを `setTimeout 0` に回し、その間に張り直されたら取り消して同じウィンドウを使い続ける（ウィンドウ名をキーにした `pendingClose`）。
- **教訓**: 外部リソース（ウィンドウ・接続・購読）を effect で確保するときは、**二重実行で作り直しても壊れないか**を先に考える。dev だけの現象でも、E2E は dev サーバーで回るので実害が出る。

## 2026-08-05: 画面を別ウィンドウに移したら、E2E とキーボードの宛先が変わる
- **事象**: 検討を別ウィンドウ化したら、既存の検討 E2E 4本が全部落ちた（本体ページには検討画面がもう無い）。ReviewBoard のショートカットも効かなくなっていた。
- **原因**: `window.addEventListener` は本体のウィンドウに張られる。createPortal は DOM だけを移すので、**JS から見た `window` は本体のまま**。
- **対策**: 描画先のウィンドウを配る `useHostWindow()` を作り、キーは必ずそこへ張る。E2E は `loadSgfForReview` が**検討画面のあるページを返す**形に変えた（ポップアップが開かなければ元のページを返す）。
- **併せて**: 生徒行の権限ボタンを名前（「着手」）で指したら、碁盤の道具列の「着手」ボタンに当たっていた。**同じ語が画面に複数あるなら testid で指す**。
- **併せて**: `readOnly` の碁盤は `data-cell` の当たり判定ごと描かれない。「打てない」ことの確認はクリックしてみるのではなく、**マス目が存在しないこと**で確かめる。

## 2026-08-05: 全面表示をやめると、それまで有り得なかった経路が開く
- **事象**: 検討を別ウィンドウに出したことで、検討中でも本体（教室ホーム）から授業・詰碁・対局を始められるようになった。そのまま移ると、生徒だけが検討画面に取り残される。
- **教訓**: 「画面を覆う」ことが暗黙の排他制御になっていた箇所は、覆うのをやめた瞬間に排他が消える。**覆いを外すときは、その覆いが何を防いでいたかを数え上げる**。今回は `endReviewIfOpen()` で終了を伝えてから移るようにした。

## 2026-08-05: 「押せないボタン」は機能の欠落ではなく、飾りが残っていた

## 2026-08-15: KataGo応答をそのまま黒勝率として表示しない

## 2026-08-23: 固有の時間方式を通常の秒読み設定へ読み替えない

## 2026-08-23: 新規作成は保存だけでなく初期表示まで初手前に検証する
- **事象**: 新規対局は正常に作成されていたが、講師の別ウィンドウは古い中断局を保持し、生徒の初手が届いて初めて新規局へ切り替わった。
- **教訓**: Realtime対局の作成確認は、INSERTの成功や初手反映だけで済ませない。作成イベントだけが届いた時点で、対局者双方が新しい対局IDと空盤を表示することを回帰テストに含める。
- **追加事象**: 新規局の終局後にも、自動フォールバックが同じ古い中断局を再表示した。
- **追加教訓**: 中断局を履歴・再開候補として保持することと、自動表示候補にすることは分ける。自動表示は `playing/scoring` だけに限定し、中断局は利用者が一覧から明示的に選んだ場合だけ開く。
- **再指摘**: 表示優先順位を直しても、講師窓が作成INSERTそのものを受信できない場合は生徒の初手まで開かなかった。作成前に別ウィンドウを開く設計では、初回fetch完了とRealtime購読開始の間にINSERTが起きる競合がある。
- **追加教訓**: 自分が開始した非同期処理の結果はRealtimeで戻ってくることに依存せず、戻り値のIDを呼び出し先へ直接渡す。別ウィンドウでは、作成後ID付きURLへ切り替えて確定済み行を再取得する。

## 2026-08-23: Realtime通知は着手の正本ではなく高速化経路として扱う
- **事象**: 生徒・講師のどちらから打っても、相手側がmoves INSERTを時々受信できず、盤面が片側だけ進んだ。
